# H1D9 checkpoints and bounded continuation

C0: clean disposable OS with trusted dependencies and this package, no CyberDefender installation/state/services. Staff must prove full-image restoration before installation. C1: installed PYTHON_ONLY baseline independently validated. C2: RUST_CANARY baseline independently validated, Python authoritative, exactly one bound native child. Record immutable hypervisor checkpoint/image identifiers, staff reference, package SHA and target UUID SHA. Checkpoint acknowledgement is an operator attestation; the harness does not create or restore snapshots.

Root cause of the old blocker: SCMStorm ended at ROLLBACK_PENDING, whose only outgoing transition was final RollbackValidate -> LAB_COMPLETE. It had no separately verified route to continue another restored fault branch.

New continuation:

ROLLBACK_PENDING -> PrepareCheckpointRestore -> CHECKPOINT_RESTORE_PENDING -> external staff restore of C2 -> ResumeCheckpoint -> C2_BASELINE_PASS.

ResumeCheckpoint executes no service/process/power action. It requires admission, external preserved-state and export hashes, exact current evidence inventory, checkpoint/session/package/machine/revision/nonce bindings, a current-boot staff receipt, fresh progressing runtime observations and authenticated store counters no older than C2. Only after these checks does it reopen the branch budget. It does not mark any test case PASS. Missing/corrupt/stale evidence or interrupted verification requires REVIEW_REQUIRED / DEGRADED_SAFE. No automatic retry. Final C0 cleanup remains PrepareRollback -> external C0 restore -> RollbackValidate; it cannot substitute for a verified C2 continuation.

Bounds: four fault debits per service per branch; 32 lifetime debits per service; 64 total lifetime debits; at most 12 verified C2 restorations; 128 history rows and 256 revisions. A storm reserves four attempts before its first actuator. Resume clears only branch debits, never lifetime counts, history, case evidence or failure results. Every legacy mutation requires an operation-bound one-use ticket, consumed durably before execution. A crash after consume loses that attempt rather than repeating it. Explicit SCMStorm permits four distinct tickets; retrying a consumed ticket is rejected.

Evidence preservation is mandatory. PrepareCheckpointRestore emits state_sha256, export_sha256, export filename and nonce. Copy the entire session results directory to staff-controlled storage outside the checkpoint, preserving every file except engine.lock/orchestrator.lock. Keep the emitted hashes separately under staff control. Verify the copy before restoring C2. Restore the **latest exported results**, not the old ledger inside C2, into the exact same session path with SYSTEM/Admin ownership and protected ACL. Do not delete counters, consumed markers, failure files or report receipts. Keep the package, authorization nonce and receipt outside the rollback domain as well. Avoid writable production-host shares; use approved isolated lab storage/media.

Use a staff-approved ACL-preserving backup tool (for example an elevated robocopy of the exact session directory with /E /COPYALL /DCOPY:DAT /XJ /XF engine.lock orchestrator.lock, without /MIR or /PURGE). Capture/verify hashes separately; a copy exit code alone is insufficient. Do not overlay an older export or merge branches by editing JSON. If the current checkpoint already contains differing evidence, stop for review; recover the preserved session into a clean designated result path with staff oversight.

The export manifest detects altered, removed or unexpected evidence files. Protected ACLs and independently retained hashes provide the trust boundary; SHA-256 is not authentication against an administrator who replaces both the data and hashes. A whole VM snapshot can roll back on-disk counters; the external preserved-state anchor is therefore required. No claim of hardware monotonic anti-rollback is made.

On an interruption during ResumeCheckpoint, preserve the in-flight record; do not rerun it. Use final C0 recovery with PrepareRollback after review. A new session is a separately authorized lab run, never an automatic way to erase a failed result. Full rollback validation also requires staff comparison of scheduled tasks, service/Registry and firewall baselines; automatic checks cover app/state directories, named services, Rust processes and ports only.
