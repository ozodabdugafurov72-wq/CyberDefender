## Entry points and evidence

In the approved guest only, verify the ZIP SHA independently, then extract it to the required C:\H1D9\package path and keep payload immutable under administrator control. Keep the original ZIP outside this folder and retain the trusted SHA from the preparation report, not a value recalculated from an untrusted transfer. Store results outside payload (e.g. C:\H1D9\results) so verification rejects additional payload files. Take OFFLINE clean checkpoint C0 after OS/dependency staging, then installed baseline C1 and stable-canary checkpoint C2. Independently rehearse checkpoint restoration before acknowledging rollback_verified. Fill the supplied authorization example OUTSIDE payload: schema, exact guest UUID SHA-256 (uppercase trimmed UUID encoded UTF-8), package_id, trusted package_sha256, disposable=true, isolated_network=true, rollback_verified=true, operator_acknowledged=true, dependencies_ready=true, clean_checkpoint=C0 identifier, a newly generated 32-character hex GUID lab_nonce, and expires_utc within the next24 hours. Empty example values deliberately deny execution. Refresh acknowledgement only after reviewing target/checkpoints; no reusable production credential belongs here. These fields prevent accidents; they do not cryptographically attest the hypervisor or resist a privileged operator rewriting the harness. Independent operator validation is required. Host UUID denial is hardcoded independently of the manifest. VM model, admin context, OS/build/resources, marker, archive SHA, schema, archived/expanded manifest and every payload byte are checked before dispatch. Reparse ancestry/duplicate/traversal/extra files fail closed. No hash bypass exists. Execution policy must be handled through the approved guest policy/signing process, never host policy changes.

Guest command prefix (run in guest elevated PowerShell):

```powershell
$g='C:\H1D9\package\payload\scripts\h1d9\guest.ps1'
$a='C:\H1D9\guest-authorization.json'
# Supply the actual transferred ZIP path and trusted SHA from package-result.json.
$zip=Read-Host 'Verified ZIP path in guest'
$sha=Read-Host 'Trusted SHA-256 from preparation report'
$bound=@{GuestAuthorization=$a;Archive=$zip;PackageSha256=$sha}
& $g -Phase Preflight @bound -Python 'C:\Python314\python.exe'
& $g -Phase Install @bound -Python 'C:\Python314\python.exe'
& $g -Phase Observe @bound -Samples 60
& $g -Phase EnableCanary @bound
& $g -Phase Observe @bound -Samples 60
```

Python path is a guest prerequisite to resolve, not an assumed installed path. All phases require x64 Windows build26100+, >=8GiB total RAM, >=3GiB free RAM and >=20GiB free C: space; denied resource admission is not a healthy result (use lab console for emergency observation/rollback). Preflight/Install refuse ANY existing CyberDefender services/app/state/crash-store. Install invokes unchanged current-source installer. EnableCanary validates installed release binary against package pin BEFORE stopping Agent, refuses an existing canary config, then writes the real runtime-config schema in guest ProgramData and starts Agent. Observe emits only selected numeric/enum/bool metadata; arbitrary runtime strings become INVALID. Missing/malformed/stale data cannot assert health. System mutation phases are not transactional: on partial failure retain evidence and restore the full guest checkpoint. No automatic repair or fallback runs.

For one exact service fault: `& $g -Phase CrashOnce @bound -Service CyberDefenderAgent`. It kills only a verified SCM process object, once, with bounded exit wait. For a clean restart use `-Phase CleanRestart` with the same arguments. Repeat each service separately, restoring checkpoint between independent destructive cases. No unattended infinite fault loop exists. Preserve UTC timestamps, boot identity, old/new PID with creation time, selected observations, sanitized authenticated offline state, ACL SDDL, SCM action readback and event IDs. Never export raw runtime telemetry, environment values, exception text, secrets, tokens, raw crash records, memory dumps or storage keys. Full checkpoint/state stays inside the disposable lab and is destroyed after retention approval.

## Exact test matrix

Restore C1/C2 between destructive cases unless the row explicitly requires persistence across them. All three services are tested independently in rows 3–9, 20–24. Observe a baseline for 120 seconds before faults; use a concurrent 600-sample observation run (20 minutes maximum). Overall abort criteria: any authority violation, orphan >10 seconds, >1 native child outside a sampled replacement transition, unexpected production/network reachability, >80% guest CPU for 30 seconds, <1 GiB guest free RAM, >512 MiB private-byte increase per service from baseline, or >100 MiB new guard/diagnostic data. ## Rollback and stop conditions

At any failed boundary stop issuing new faults, keep production untouched, pause/power off ONLY the identified disposable VM through its lab console, retain sanitized observations, and revert the whole guest to the named checkpoint. Restore OS disk, application, ProgramData, CrashGuard key/anchor/state, SCM and registry together; never transplant guest keys/state into production. Destroy the disposable VM/disks only after evidence retention is approved. Source preparation added new scripts/docs/evidence only; prior H1D files are byte-verified unchanged and backed up. No deletion/cleanup automation runs on this host.

Readiness requires an approved target identity, supported VM platform, sufficient resources, verified ZIP and prerequisites, C0/C1/C2 checkpoint workflow, guest policy for scripts, selected debugger/fault tools, observer and abort supervision.
